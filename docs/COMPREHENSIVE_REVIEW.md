# الجزء الأول: الاكتشاف والفهم

## 1. الملخص التنفيذي

«دفتري» (الحزمة `com.daftari.ledger`) تطبيق **Android أصلي أوفلاين بالكامل** لدفتر حسابات التاجر وصاحب المحل الصغير، مبني من الصفر بـ Kotlin + Jetpack Compose + Room، عربي RTL أولًا، بوظائف محاسبة فعلية (قيد مزدوج داخلي، عملاء/موردون، بيع/شراء/مصروف/إيراد/تحصيل/سداد/تحويل)، دفتر بيع يومي، نظام موظفين وصلاحيات وورديات، شريحة مخزون وفواتير، تقارير وتصدير (PDF/Excel/CSV)، ونسخ احتياطي متعدد الطبقات (محلي/مشفّر/Google Drive/WebDAV/SAF) — مع إصدار `1.3.0` (versionCode 4)، وقاعدة بيانات Room إصدار 8 بترحيل كامل 1→8.

**الحكم المختصر:** مشروع **فوق المتوسط بوضوح**، بأساس هندسي سليم لا يحتاج إعادة بناء. نقاط قوته نادرة (المنطق المحاسبي الصرفي، ونظام النسخ الاحتياطي، والاهتمام بالعربية). لكنه يحمل: خطأ بناء حرجًا واحدًا، فجوات في فرض الصلاحيات، فواتير "تُنشأ وتختفي بنودها"، وتضخمًا تدريجيًا في حالة الواجهة. **القرار: تحسين تدريجي مركز، وإعادة هيكلة جزئية لطبقة العرض فقط.**

## 5. البنية

ثلاث طبقات واضحة **[حقيقة — طابقتها الوثائق]**:
```
UI (Compose + MainViewModel + StateFlow + UiEvent/UiEffect)
   → Domain (دوال صرفية: Money, JournalLineBuilder, AgingFifo, InventoryMath, SalesBookAnalytics, StaffPermissions)
   → Data (LedgerRepository/StaffRepository → DAOs → Room/SQLite)
```
- **حقن يدوي** (لا Hilt): `DaftariApp` يبني `AppDb/repo/staff/backup` ويُمرَّر لـ `MainViewModel`. **[حقيقة]** — مقبول للحجم، لكنه يعيق الـ mocking في الاختبار.
- **مصدر الحقيقة:** SQLite محلي. الأموال `Long` بوحدة صغرى، ممنوع Float/Double. **[حقيقة]**
- **النمط:** Repository + MVVM + دوال صرفية قابلة للاختبار (جودة نادرة).

## 6. تدفق البيانات

**مسار العملية (بيع آجل):**
```
المستخدم → DocumentSheet → UiEvent.AddDocument → MainViewModel.addDocument
→ (تحقق صلاحية في VM) → Money.fromMajor → repo.postDocument → db.withTransaction:
    validatePartyAndPayment/validatePartyKind → fiscal check → رقم السند
    → refsFor() → documents.insert → JournalLineBuilder.build() (مدين ذمم/دائن مبيعات)
    → journal.insertAll → refreshPartyBalance → audit.insert
→ refreshAll() → refreshTotals/Insights/SalesLedger + تحديث الويدجت → StateFlow → إعادة رسم
```
**تدفق الملاحظة:** `Flow` من Room → `collectLatest` → `MutableStateFlow.update`. **تدفق النسخ:** لقطة ← فحص `quick_check`/`foreign_key_check`/`DatabaseHealthCheck` ← أرشفة/تشفير/رفع ← فحص checksum ← استعادة ذرّية + `AppDb.invalidate` + إعادة تشغيل العملية.

## 9. تحليل UX/UI

**نقاط قوة (مع الأدلة):** تسلسل بصري سليم (HeroMetric «صافي النقد» ثم SplitMetric «لك/عليك»)؛ تلوين دلالي ثابت (أخضر=لك/أحمر=عليك)؛ رسائل لغير المحاسب؛ حالات فارغة موجهة؛ NavigationRail للعريض وشريط سفلي للهواتف؛ Snackbar تراجع؛ وضعان داكن/فاتح؛ عدادات متحركة.

**اكتشافات/عيوب UX:**
1. **رمز العملة:** `Money.format` يستخدم `NumberFormat.getCurrencyInstance(locale)` ثم يضبط `currency = Currency.getInstance(code)` **دون ضبط الرمز**، و`displayMoney` يستخدم `Locale.US` عند `latinDigits=true` (الافتراضي) → سيُعرض «$» بدل «﷼/ر.س». **[استنتاج قوي]**
2. **«آخر حركة»:** بطاقة المتأخرين تعرض `stringResource(R.string.last_activity, MIN(dueAt))` — أي **أقدم تاريخ استحقاق** وليس آخر حركة. **[حقيقة — تسمية مضللة]**
3. **اثنان من «إغلاق اليوم»:** `section_day_close` (More = `daily_closings` + عدّ نقد فعلي) و`close_sales_day` (تبويب البيع = `daily_books` للقراءة فقط) — **نفس التسمية، دلالتان مختلفتان**. **[حقيقة — ارتباك منتج]**
4. **كثافة «المزيد»:** 11 قسمًا أكورديون — منظم لكنه طويل.
5. **`FLAG_SECURE` دائم** يمنع تصوير شاشة المستخدم نفسه (قرار خصوصية يحد من الإنتاجية).
6. **بنود الفاتورة غير مرئية بعد الإنشاء** (انظر §28) — المستخدم لا يرى تفاصيل فاتورته لاحقًا.

## 11. تحليل المنتج (Product)

- **Core Value (20% التي تصنع 80%):** البيع السريع + الأرصدة الفورية (لك/عليك) + التحصيل + النسخ الاحتياطي.

# الجزء الثالث: الهندسة العميقة

## 14. تحليل الكود

**إيجابيات (مؤكدة):** دوال صرفية مختبرة؛ `withTransaction` في كل كتابة متعددة الجداول؛ بناء القيد قبل الإدراج؛ حماية سباق (`totalsMutex`، `shopBindJob.cancel`، `MutableStateFlow.update`)؛ ثوابت `AccountCodes`؛ **لا TODO/FIXME/HACK**.

**مشاكل (مرتبة):**
1. **MainViewModel ضخم** (~624 سطرًا + 6 امتدادات) + `UiState`/`UiEvent` ضخمان → صيانة متعثرة متدرجة.
2. **فرض صلاحيات غير موحّد** (تفصيل في §28/§31).
3. **`importCsv`:** عدّاد `ok++` يُحتسب حتى مع مبلغ تالف؛ `occurredAt` دائمًا "الآن". **[حقيقة]**
4. **`InventoryMath.parseQty`:** `"-0.5"` → +500 (خطأ إشارة)؛ `"1.5.5"` تُفسَّر 1.5 بصمت. **[حقيقة]**
5. **تعديل الفاتورة من الشاشة العامة** يغيّر المبلغ دون البنود/المخزون (انظر §28). **[حقيقة]**
6. **`updateDocument` لا يفحص السنة المالية** (بينما `postDocument` يفحصها). **[حقيقة]**

## 15. تحليل البيانات

- **النموذج:** 15 كيانًا + FTS4؛ `Long` PK autoGenerate؛ علاقات `RESTRICT`؛ أرشفة ناعمة؛ فهارس جيدة.
- **الترحيل:** كامل 1→8، اختبار `MigrationTestHelper`، بلا destructive fallback. **[حقيقة]**
- **فحص صحة:** `DatabaseHealthCheck` (يتيم/توازن/نوع طرف/تطابق محل/تطابق cached) — طبقة دفاع نادرة.
- **ملاحظات:** `daily_closings/daily_books/employees*` بلا Foreign Keys في الكيان (تعويض بفحص الصحة — قرار موثّق)؛ `cachedBalanceMinor` حقيقة عرض معاد حسابها في المعاملة ومراقبة بفحص الصحة؛ **لا تنظيف للبيانات المؤرشفة** (نمو دائم).

## 16. تحليل الأداء

- **قوي:** FTS4؛ LIMIT؛ تصدير على IO؛ `collectLatest`؛ حماية تراكم الاشتراكات.
- **مخاطر:** `salesBookDays` يحمّل كل مستندات الفترة في الذاكرة ثم يكرر يوميًا؛ `exportCsv`/`ExcelReports` يقرآن `listPeriod(0..MAX)` كاملًا؛ `refreshTotals` يحسب 3 فترات+فئات+أرصدة لكل تغيير.
- **بدء التشغيل:** سريع (القاعدة تُفتح فورًا)؛ `hasLocalData()` تُستدعى عند إنشاء VM (استعلامات COUNT متعددة).

## 17. تحليل الأمن

**قوي:** PBKDF2-HMAC-SHA256 (120k) + توافق خلفي آمن؛ AES/GCM للنسخ؛ كلمة WebDAV في EncryptedSharedPreferences؛ لا تخزين رموز Google؛ `allowBackup=false`؛ `exported=false` لـ FileProvider؛ حماية zip-slip وحجم أقصى.

**مشاكل (مرتبة بالخطورة):**
1. **[متوسط]** فرض صلاحيات غير كامل في المستودع (العمليات الحساسة تعتمد على إخفاء الأزرار فقط) + صلاحية **قراءة** (`VIEW_ACCOUNTS`) تُستخدم بوابة لكتابة (PURCHASE/COLLECT/PAY/TRANSFER، وفاتورة الشراء) **[حقيقة]**.
2. **[منخفض]** تسجيل بريد Google في Logcat (`Log.d(...,"for account: $email")`).
3. **[منخفض]** فك JWT محليًا (`decodeGoogleSubject`) دون تحقق من التوقيع (يُستخدم لربط مبكر فقط، والتحقق النهائي عبر `userInfo`).
4. **[منخفض]** `security-crypto:1.1.0-alpha06` (ألفا لمكتبة أمنية حرجة).
5. **[منخفض]** PIN موظف 4 أرقام + قفل 30 ثانية فقط.
6. **[ملاحظة]** Client ID عام مُضمّن كافتراضي (ليس سرًا، لكنه يربط البناء بمشروع المطوّر).

## 18. تحليل الاختبارات

- **موجود:** 13 JVM + 4 androidTest (منطق/ترحيل/تكامل/فحص صحة/دفتر بيع/Drive بمحاكي MockWebServer).

## 44. رأي مهني صريح

المشروع **جيد فعلًا** وليس مجرد "كود يعمل". الأساس **قوي** ويستحق الاستمرار. يحتاج **إصلاحًا** (لا إعادة هيكلة شاملة ولا إعادة بناء) في الأمان والتشغيل، وإعادة هيكلة **جزئية** لطبقة العرض. أكبر نقطة قوة: المنطق المحاسبي والنسخ الاحتياطي. أكبر نقطة ضعف: كسر قابلية البناء + فجوات الصلاحيات. أخطر مشكلة: تناقض الفواتير/المخزون الصامت. أكبر فرصة: "محاسبة عربية أوفلاين صحيحة + تقارير ضريبية". الشيء الذي لو أصلحناه يتغير المستوى بوضوح: **فرض الصلاحيات المركزي + إكمال دورة الفاتورة + إصلاح CI**. لو كنت المسؤول: أولًا إصلاح Wrapper وCI، ثانيًا توحيد فرض الصلاحيات، ولن ألمس أبدًا المنطق المحاسبي والنسخ ونموذج البيانات.

## 48. أهم 10 أفكار لم تكن واضحة من البداية
1. الفواتير تُنشأ وبنودها لا تُعرض — يحتاج "دورة فاتورة كاملة".
2. "آخر حركة" هي في الواقع "أقدم استحقاق" (تسمية مضللة).
3. اثنان من "إغلاق اليوم" بنفس الاسم ودلالتين مختلفتين.
4. Excel "أرقام كنصوص" (فقط عند المحاولة في Excel).
5. `importCsv` يعدّ نجاحًا كاذبًا (مبالغ تالفة) ويسجل التاريخ "الآن".
6. `parseQty("-0.5")` تعطي +500 (خطأ إشارة).
7. الويدجت يعرض أول محل لا المحل النشط.
8. DataStore معلنة وغير مستخدمة.
9. قفزة رقم السند عند إدخال رقم مخصص كبير.
10. `.gitignore` تالف UTF-16 (قد يسمح بتتبع ملفات zip).

## 50. مراجعة التغطية النهائية

فحصت كل ملفات Kotlin (12,951 سطرًا) وXML وGradle/CI/proguard/schemas/الاختبارات/الوثائق/الـ gitignore وتاريخ Git. غطيت: الوظائف، مسارات المستخدم، الحالات الطبيعية/غير الطبيعية، الأمن، البيانات، UX، المنتج، السوق، المنافسين، القابلية للتوسع، المستقبل، التناقضات، الافتراضات، المشكلات الصامتة، إمكانية الوصول، التوطين، الثقة. **حاولت إسقاط استنتاجات الجولة الأولى** فأكّدت معظمها وصحّحت/عمّقت اثنين: (1) أرشفة الفاتورة تعكس المخزون بشكل **صحيح** (نقطة قوة لم أذكرها بدقة في الجولة الأولى)، (2) المشكلة محصورة في **التعديل** لا الأرشفة، مع غياب تام لعرض البنود. **فكرت كمنافس ومستخدم ومستثمر ومالك ومهندس ومصمم.** لم أجد ما يعكس الحكم العام: الأساس سليم، والجوهر يجب ألا يُمس.

### الحكم النهائي (مكثف)
**هل المشروع جيد؟** نعم — جيد جدًا كنواة منتج. **هل الأساس قوي؟** نعم. **يستحق الاستمرار؟** بلا تردد. **إصلاح أم إعادة هيكلة أم إعادة بناء؟** إصلاح تدريجي + إعادة هيكلة جزئية للعرض فقط. **أكبر قوة:** المنطق المحاسبي + النسخ الاحتياطي. **أكبر ضعف:** كسر البناء + فجوات الصلاحيات. **أخطر مشكلة:** تناقض الفواتير/المخزون الصامت. **أكبر فرصة:** المحاسبة العربية الأوفلاين الصحيحة + الضريبة المحلية. **ما يغيّر المستوى جذريًا لو أُصلح:** فرض الصلاحيات المركزي + دورة الفاتورة الكاملة + CI حقيقي. **أولًا:** إصلاح Wrapper. **ثانيًا:** توحيد الصلاحيات. **لا ألمس أبدًا:** المنطق المحاسبي والنسخ ونموذج البيانات. **أفضل نسخة ممكنة:** دفتر بيع/تحصيل فوري، فواتير كاملة، تقارير ضريبية بنقرة، نسخ لا يُضاهى، وبساطة تجعل التاجر الصغير يثق ببياناته ثقة الورق.
